# EventFlow — аудит производственной основы

**Дата:** 13 ноября 2026 года  
**Репозиторий:** `PelzA83/EventFlow` (закрытый)  
**Назначение документа:** зафиксировать фактическое состояние существующей базы перед подготовкой процесса выполнения индивидуальных заказов.

## 1. Краткий вывод

Закрытый репозиторий уже содержит раннюю основу приложения и SQL-снимки, поэтому начинать с пустого проекта не требуется. Однако текущую версию нельзя считать готовой производственной базой для новых заказов.

В репозитории находятся:
- ранняя гостевая страница `index.html`, подключённая к Supabase;
- ранний `organizer.html`, который по текущему коду не демонстрирует интеграцию с тем же backend;
- SQL-схема и RPC-функции для базового сценария приглашения и RSVP;
- утверждённые спецификации 1.0–1.2 и дорожная карта.

Актуальная публичная демонстрация в `PelzA83/eventflow-demo` — другая, более поздняя ветка реализации: текущие `demo.html`, `demo-organizer.html`, `demo-guest.html` и `demo-worker.js` используют SharedWorker с данными в памяти. Это полезная проверенная UX- и функциональная основа, но не постоянное хранилище и не готовый production backend.

**Вывод:** не копировать целиком ни одну из двух реализаций в производственную основу. Сначала определить, какие проверенные пользовательские сценарии и компоненты переносим из публичной Demo, а затем согласовать постоянную модель хранения и серверную логику на основании спецификаций.

## 2. Состав закрытого репозитория

На момент аудита в корне:

В закрытом репозитории не обнаружены `AGENTS.md` и `docs/PROJECT_STATUS.md`. Их отсутствие не заменяется этим аудитом; при необходимости правила работы и контрольную точку проекта следует оформить отдельно.

## 3. Состояние файлов приложения

### `index.html` — гостевая страница

- Содержит визуальную страницу приглашения и RSVP-форму.
- Подключает клиент Supabase и использует publishable key.
- Загружает приглашение через RPC `get_invitation`.
- Отправляет ответы через RPC `submit_rsvp`.
- По структуре это ранний сценарий гостевого приглашения, а не текущая модель всех согласованных возможностей EventFlow.

SHA при аудите: `82d4d38211ca4915643b333fb437a9309563a654`.

### `organizer.html` — кабинет организатора

- Содержит ранний интерфейс входа и кабинета.
- В просмотренном клиентском коде не обнаружены вызовы Supabase, RPC или fetch для синхронизации данных.
- Поэтому нельзя считать, что этот кабинет работает с теми же постоянными данными, которые использует гостевая страница.

SHA при аудите: `e9801815c2a9c669459d8e1297def62ecab3f7f3`.

### SQL-снимки

В каталоге `database/` находятся:
- `01_database_schema.sql` — базовые таблицы мероприятий, групп, гостей и RSVP, индексы и включение RLS;
- `02_seed_data.sql` — тестовые начальные данные;
- `03_get_invitation.sql` — RPC получения приглашения по токену;
- `04_submit_rsvp.sql` — RPC сохранения RSVP;
- `05_rsvp_tests.sql` — тестовые SQL-запросы.

Эти файлы являются снимками в репозитории, а не доказательством текущего состояния удалённой базы данных. Их нельзя запускать повторно без отдельной сверки с фактической схемой. Seed SQL не запускать повторно.

В частности, текущая ранняя схема не покрывает всю согласованную модель EventFlow: жизненный цикл приглашений, отдельные записи участников и историю, исключение/архивацию, индивидуальные продления RSVP, версии QR, расширенную статистику и другие согласованные правила требуют отдельной проверки и проектирования.

## 4. Сопоставление с публичной Demo

Публичный репозиторий `PelzA83/eventflow-demo` содержит более актуальную демонстрацию пользовательских сценариев:
- общий интерфейс организатора и гостевую страницу;
- универсальные блоки и управление их видимостью/порядком;
- персонализацию приглашения;
- демонстрационные RSVP и QR;
- ряд уже проверенных пользователем визуальных и поведенческих сценариев.

Но текущая Demo использует SharedWorker и хранит данные в памяти активной сессии. Она не обеспечивает постоянное хранение и не является production backend.

Следовательно:
- публичную Demo используем как источник актуальных UX-решений и проверенных сценариев;
- закрытый репозиторий сохраняем как место для спецификаций и будущей производственной основы;
- перенос кода выполняем выборочно, после проверки зависимостей и согласования способа хранения данных;
- не смешиваем старый Supabase-сценарий закрытого репозитория с временной архитектурой SharedWorker из Demo.

## 5. Что необходимо подготовить до первого реального заказа

1. **Единая контрольная точка кода.** Определить, какие версии файлов и сценариев являются исходной точкой производственного проекта.
2. **Разделение ядра и оформления.** Отделить функциональные блоки и данные от дизайн-шаблона, чтобы один сценарий можно было оформлять несколькими способами.
3. **Экземпляр заказа.** Определить, как из общей основы создаётся отдельный проект клиента, не перезаписывающий ядро и другие заказы.
4. **Данные и конфигурация.** Разделить общие настройки шаблона и индивидуальные материалы: тексты, изображения, цвета, шрифты, данные мероприятия и список гостей.
5. **Хранение и безопасность.** Определить постоянное хранилище, доступы, правила RLS/серверных операций и обращение с персональными ссылками. Секреты не должны попадать в публичный репозиторий или клиентский код.
6. **Проверка и публикация.** Зафиксировать короткий процесс проверки на тестовых данных, согласования с заказчиком, публикации и сохранения версии.
7. **Возврат к внутренней разработке.** Сохранять состояние дорожной карты до переключения на заказ и продолжать с него после завершения заказа.

## 6. Рекомендуемый порядок дальнейшей подготовки

1. Не менять существующие рабочие файлы и SQL до определения целевой основы.
2. На основании спецификации 1.2 и актуальной Demo составить карту: «уже есть», «есть только в Demo», «нужно реализовать для производственного сценария».
3. Отдельно определить минимальный производственный контур первого заказа: один продукт, один дизайн-шаблон, индивидуальные данные клиента, безопасная публикация.
4. Только после этого подготовить структуру каталогов и переносить проверенные компоненты.
5. Проверять каждый небольшой шаг отдельно; не объявлять код готовым до фактической проверки сценария.
